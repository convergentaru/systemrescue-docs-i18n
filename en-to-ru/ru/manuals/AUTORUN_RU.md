# Запуск собственных скриптов с autorun

## Обзор Autorun

Функция **autorun** позволяет запускать скрипты или бинарные программы автоматически при старте системы. Каждый авторун-скрипт может управлять задачей. Например, вы можете создать скрипт резервного копирования, который делает резервную копию базы данных, другой для очистки системы и т.д.

По умолчанию скрипты autorun могут быть скопированы в директорию `autorun` образа ISO или устройства загрузки, вне сжатого файла squashfs, но доступны и другие источники: локальная файловая система, сетевая share, HTTP/HTTPS сервер.

## Способы конфигурации

SystemRescue предлагает два способа конфигурации авторун-программ:

* **Name based**. Программы с именем файла начинающимся с `autorun` в наборе мест загружаются и выполняются. Это старый стиль конфигурации autorun.
* **YAML config based**. Файл конфигурации содержит пути, URL и параметры для столько авторун-программ сколько необходимо. Это новый стиль конфигурации autorun, доступный с версии SystemRescue 9.05.

Оба метода полностью поддерживаются и планируется оставить их доступными в будущих релизах.

## Конфигурация autorun с YAML

Синтаксис:

```yaml
---
autorun:
    exec:
        200:
            url: "http://web-server/adminscripts/some-script"
            parameters: 
                - "foo"
                - "bar"
            shell: false
            wait: always
            waitmode: 15
            on_error: break
        300:
            path: "rclone"
            parameters: 
                - "copy"
                - "myserver:/scripts/"
                - "/root"
            wait: on_error
            on_error: break
```

Конфигурация делается через записи в [YAML configuration](/manual/Configuring_SystemRescue/) используя записи `exec` в области действия `autorun`. Ключи в Mapping/словаре `exec` (`200` и `300` в примере выше) — это имена для каждой авторун-программы. Программы выполняются в лексикографическом порядке этих имён.

Опции для каждой записи `exec`:

* Каждая авторун-программа должна иметь одну запись `url` или `path`, но не может иметь обе
* **url** — URL для загрузки программы. Поддерживаются протоколы http, https, nfs и smb, также пути устройств ниже /dev.
  * При использовании https сертификат сервера проверяется на валидность. Убедитесь, что системные часы правильны. Вы можете [добавить свои сертификаты в trusted CA store](/manual/Configuring_SystemRescue_sysconfig/) если необходимо.
  * nfs использует стиль `nfs://hostname:/path/script`
  * smb использует стиль `smb://hostname/share/path`. Обратите внимание, что поддерживаются только публичные гостевые share без пароля.
  * Вы также можете предоставить путь в незамонтированное блочное устройство, например `/dev/sda1/usr/bin/script` или `/dev/disk/by-label/mylabel/usr/bin/script`.
* **path** используется для программ на уже замонтированных устройствах.
  * Поддерживаются абсолютные пути или lookup в $PATH
  * Используйте `/run/archiso/bootmnt/autorun/` для доступа к скриптам в директории `autorun` на загрузочном носителе.
  * Эта директория также копируется при использовании опции `copytoram`, тогда как другие части загрузочного носителя не доступны при использовании `copytoram`.
* **parameters** — список параметров, передаваемых программе.
* **shell** (по умолчанию: `false`) контролирует, выполняется программа напрямую или через оболочку `/bin/sh`.
  * При использовании оболочки все заданные параметры конкатенируются и передаются оболочке как одна строка. Разделение затем делается оболочкой.
  * Правильное экранирование параметров должно быть сделано пользователем.
  * Рекомендуется не использовать опцию shell если не необходимо, например для piping вывода в другую программу.
  * Shell-скрипт может (и обычно должен) выполняться напрямую и без этой опции shell. Эта опция о том как скрипт вызывается и передача параметров, а не языке на котором написан скрипт. Shebang распознаётся при прямом выполнении и без опции shell.
* **wait** разрешённые значения `always`, `on_error` или `never`, по умолчанию `on_error`. Контролирует если/когда ждать прямо после выполнения этого одного скрипта.
* **waitmode** позволяет либо `key` для требования нажатия клавиши, либо число, указывающее количество секунд для ожидания. Вы можете нажать клавишу чтобы продолжить до того как заданное количество секунд истечёт. По умолчанию `30`.
* **on_error** позволяет либо `break` или `continue`, с `ar_ignorefail` контролирующим дефолт. Определяет что делать со следующими скриптами после того как этот скрипт провалился (вернул non-zero статус).

## Name based autorun

Скрипты для выполнения ищутся используя список правил (см. ниже). Если скрипты найдены, записи в Mapping/словаре `exec` создаются для них. Это позволяет использовать YAML based autorun и name based autorun программы вместе.

### Опции для name based autorun

* **ar_source=xxx**: место где расположены autorun. Может быть корневая директория устройства (`/dev/sda1`), nfs share (`nfs://192.168.1.1:/path/to/scripts`), samba share (`smb://192.168.1.1/path/to/scripts`) или http/https директория (`http://192.168.1.1/path/to/scripts`). Пожалуйста обратите внимание этот параметр содержит адрес папки которая содержит некоторые авторун-скрипты. Это не полный адрес конкретного скрипта, так как имя скрипта будет добавлено в конце источника.
* **ar_suffixes=[0-F]**: запятая разделённый список суффиксов соответствующих авторун-скриптам которые должны быть выполнены. Например если вы используете `ar_suffixes=0,2,7` то следующие авторун-скрипты будут выполнены: `autorun0`, `autorun2`, `autorun7`, и скрипты с другими суффиксами будут игнорироваться. Используйте `ar_suffixes=no` чтобы отключить все авторун-скрипты с суффиксом.

### Правила поиска скриптов для name based autorun

При старте список мест проверяется на наличие авторун-файлов. Они, последовательно:

* если параметр **ar_source=** был передан при старте, корневая директория данного места.
* папка **autorun** расположенная у корня загрузочного устройства (с версии SystemRescue 9.00)
* домашняя директория суперпользователя (**/root**)
* директория **/usr/share/sys.autorun**

Если авторун-файлы найдены в некотором месте, они добавляются в Mapping/словарь `exec` и следующие места игнорируются.

В каждом источнике места есть два возможных режима работы:

* простой: если найден shell-скрипт названный `autorun`, он запускается
* более гибкий: если найдены скрипты `autorun#` (# — цифра от 0 до 9 или буква от A до F) и либо
  * параметр загрузки **ar_suffixes=** НЕ был указан, или
  * значение параметра **ar_suffixes=** содержит #

Пример: с `ar_suffixes=0,1,4` только скрипты `autorun0`, `autorun1` и `autorun4` будут выполнены если присутствуют. Другие скрипты, такие как `autorun2` и `autorun3` будут игнорироваться.

Скрипт с именем файла `autorun` получит имя `1000-autorun` внутри Mapping/словаря `exec`. `autorun0` получит `1010-autorun0`, `autorun1` будет `1011-autorun1` и так далее до `1025-autorunF`. Эта схема нумерования позволяет контролировать порядок выполнения при использовании YAML config based autorun вместе с name based autorun.

## Общие опции для autorun

Эти опции используются для контроля общего поведения autorun. Они могут быть указаны либо на командной строке загрузки, либо через [YAML configuration files](/manual/Configuring_SystemRescue/).

* **ar_nowait**: не ждать нажатия клавиши после выполнения всех авторун-скриптов (по умолчанию: true)
* **ar_ignorefail**: продолжать выполнять цепочку скриптов даже если скрипт провалился (вернул non-zero статус) (по умолчанию: false)
* **ar_nodel**: не удалять временную копию авторун-скриптов расположенных в `/var/autorun/tmp` после выполнения (по умолчанию: false)
* **ar_disable**: полностью отключить все выполнение autorun (по умолчанию: false)
* **ar_attempts** — количество попыток скачать скрипт с удалённого URL (по умолчанию: 1)

## Установка авторун-программ

Самый простой способ поместить авторун-программы на носитель SystemRescue — это создать загрузочный USB-носитель для SystemRescue с поддержкой записи. Это можно сделать с Rufus или SystemRescue USB writer [как описано здесь](/Installing-SystemRescue-on-a-USB-memory-stick/). После этого вы можете смонтировать USB-носитель и скопировать авторун-скрипты в директорию `autorun` с помощью обычного менеджера файлов.

Если вы устанавливаете SystemRescue на флешку используя либо `dd`, либо любой другой инструмент который выполняет физическую копию образа ISO, это не создаст файловую систему с возможностью записи, и вы не сможете скопировать авторун-скрипты на устройство.

Если создание загрузочного носителя с поддержкой записи невозможно, вы можете модифицировать образ ISO с помощью [sysrescue-customize](/scripts/sysrescue-customize/).

Для записи программ в директорию `/root` или `/usr/share/sys.autorun`, вам нужно модифицировать не загрузочный носитель, а файловую систему к которой загружается SystemRescue (airootfs). Это лучше всего достигается использованием [SystemRescue Modules (SRM)](/Modules/) или с [permanent backing store](/manual/Creating_a_backing_store/).

## Выполнение программ

Скрипт может быть любым скриптом использующим установленный интерпретатор типа shell, Python, Perl и т.д. Он должен иметь shebang (#!) в начале чтобы указать используемый интерпретатор. ELF бинарники также поддерживаются.

Авторун-программы выполняются на основном системном консоли. Весь их вывод пишется на консоль и ввод с консоли передаётся программе. Escape sequences не передаются, поэтому используя curses based text UI (например как `setkmap`) не поддерживается. Для программ с пользовательским взаимодействием использование [autoterminal](/manual/autoterminal_scripts_on_virtual_terminal/) является предпочтительным решением над autorun.

## Troubleshooting

С версии SystemRescue 9.00 вы можете найти общий файл лога autorun в `/var/log/sysrescue-autorun.log` чтобы определить что пошло не так. Используйте этот лог файл если у вас общая проблема с авторун, например если ваш скрипт не был выполнен. Вывод авторун также логируется в systemd journal.

Каждый авторун-скрипт дополнительно создаёт свой собственный лог-файл и файл с returncode в `/var/autorun/log`. Используйте эти логи для исследования проблем влияющих на конкретный авторун-скрипт.

Для отладки может быть полезно перезапустить autostart позже когда система уже запущена. Вы можете это сделать вызвав `/etc/systemd/scripts/sysrescue-autorun`.
